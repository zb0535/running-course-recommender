# 러닝 코스 추천 — 추천 모델 · 데이터 · API

사용자 조건(거리·시간·페이스·목적·동반자)과 현위치로 러닝 코스를 추천하고, 실제 보행 경로와 턴바이턴 안내를 내려주는 FastAPI 서버.

> 발표 자료(진도 점검·중간 점검 대비): [docs/발표자료.md](docs/발표자료.md)

## 빠른 시작

**Python 3.10 이상 필요** (3.10 ~ 3.14, 아나콘다 3.11에서 확인). `python --version`으로 먼저 확인하세요.

```bash
git clone https://github.com/G100/running-course-recommender.git
cd running-course-recommender
python -m venv .venv
.venv\Scripts\activate            # macOS/Linux: source .venv/bin/activate
python -m src.setup_local          # 기준 환경과 똑같이 맞춘다 (처음 한 번, 약 10~15분)
python -m uvicorn src.api.main:app --reload
```

`python -m src.setup_local`이 하는 일 (이미 된 단계는 건너뜀):

1. 파이썬 3.10 이상인지 확인
2. 패키지 설치 (`requirements.txt` + 지도 변환용 `requirements-map.txt`)
3. `.env`가 없으면 만들고, 비어 있는 API 키를 알려줌 → **키 값은 팀 채널에서 받아 넣는다** (시스템 환경변수에 넣어도 된다)
4. 팀 기준 날짜로 고정한 한국 OSM 파일(약 290MB)을 받고 MD5로 같은 파일인지 확인
5. 로컬 지형 DB를 만듦 (약 8분, 880MB). 기준과 다른 DB가 있으면 다시 만듦
6. 인도 확인 기록을 저장소의 씨앗 파일(`data/sidewalk_facts.seed.json`)로 시작
7. 테스트를 돌리고 기준과 비교한 결과를 보여줌

끝에 `✔ 기준 환경과 같습니다`가 나오면 된다. 서버를 띄운 뒤 http://localhost:8000/health 에서 `local_map.matches_team: true`, `local_map.elements: 2052310`이면 기준 PC와 같은 지도다. 같은 지도·같은 코드·같은 인도 확인 기록이므로 같은 요청에 같은 코스가 나온다.

**맞추지 않는 것**: API 키(각자 `.env`), 각자 쌓인 사용자 데이터(`data/app.sqlite` — 취향·평가·로그인), 쓰면서 늘어나는 인도 확인 기록. 기록을 팀과 다시 맞추려면 한 사람이 `python -c "from src.recommend.sidewalk import export_seed; print(export_seed())"`로 씨앗 파일을 갱신해 커밋한다.

- 데모 화면: http://localhost:8000
- API 문서(직접 호출 가능): http://localhost:8000/docs
- 테스트: `python -m pytest`

> `git pull` 후에는 `python -m src.setup_local`을 다시 실행하세요. 바뀐 것만 반영하고(패키지, 지도 DB 버전), 이미 같은 것은 건너뜁니다.

## API 키

`.env`에 입력합니다. 키는 저장소에 없으며, 커밋하면 안 됩니다(`.env`는 `.gitignore` 대상).

| 키 | 용도 | 없으면 |
|---|---|---|
| `TMAP_APP_KEY` | DB에 없는 지역의 실시간 코스 생성 | 해당 요청만 `503` |
| `KMA_API_KEY` | 실시간 날씨 반영 | 날씨 미반영 |

지도 표시, DB 코스 추천, 턴바이턴 안내는 **키 없이 동작**합니다. 설정 상태는 `/health`에서 확인할 수 있습니다(값은 노출 안 됨).

### `POST /recommend` 요청

모든 필드는 선택입니다.

| 필드 | 값 | 설명 |
|---|---|---|
| `preferred_distance_km` | 숫자 | 목표 거리 |
| `preferred_time_min` | 숫자 | 거리 대신 시간으로 지정 (페이스로 환산) |
| `pace_min_per_km` | 숫자 | 평소 페이스(분/km). 모르면 생략 |
| `experience_level` | `beginner` `intermediate` `advanced` | 페이스를 모를 때 추정에 사용 |
| `purpose` | `/onboarding/purposes` 값 | 고도 목표·가중치 조정 |
| `companion` | `/onboarding/companions` 값 | 가중치 조정 + 거리·고도 상한. 목록에 없는 값은 `422` |
| `environment_tags` | `/onboarding/scenery`의 `value` (예: `"바다"`) | 고르면 필수 조건. 목록에 없는 값은 `422` |
| `text` | 문장 | 자연어에서 태그 추출 (예: "바다 보이는 코스") |
| `elevation_preference` | `low` `medium` `high` | 목적이 없을 때 고도 기준 |
| `route_type` | `roundtrip`(기본) `loop` `oneway` | 왕복(갔던 길로 되돌아옴) / 순환(한 바퀴 돌아 제자리, 현위치 필요) / 편도 |
| `destination` | 장소 이름 | 목적지 지정 (예: "오동도"). 주면 추천 대신 그곳까지 경로를 만듦. 현위치 필요. 이름만 주면 현위치에서 가까운 첫 후보로 정하고, 코스에 `destination`(정한 곳)과 `destination_alternatives`(다른 후보)를 같이 줌 |
| `destination_lat`, `destination_lng` | 좌표 | 장소 이름 대신 좌표로 목적지 지정 |
| `current_lat`, `current_lng` | 좌표 | 현위치. 반경 내 DB 코스가 없으면 실시간 생성 |
| `max_distance_km` | 숫자 (기본 5) | 현위치 기준 DB 코스 탐색 반경 |
| `time_of_day` | `morning` `afternoon` `evening` `night` | 생략하면 서버 시각으로 자동 판단 |
| `use_live_environment` | `true`(기본) / `false` | 실시간 날씨 반영 여부 |
| `top_n` | 숫자 (기본 5) | 결과 개수 |
| `user_id` | 문자열 | 주면 그 사람이 평가로 학습한 가중치로 추천. 첫 요청의 온보딩 값이 초기 설문으로 저장됨 |

### 응답

```jsonc
{
  "source": "db",                  // "db" | "generated"(실시간 생성) | "destination"(목적지 지정)
  "results": [{
    "score": 0.84,
    "score_breakdown": { "distance": 1.0, "signal_free": 0.92, "safety": 0.88, ... },  // 왜 이 코스인지
    "rating": { "average": 4.5, "count": 12 },   // 다른 사용자들의 별점 (없으면 null)
    "favorite": false,                           // user_id를 줬을 때, 내가 즐겨찾기한 코스인지
    "course": {
      "name": "...", "distance_km": 5.0, "elevation_gain_m": 58, "safety_score": 0.88,
      "path": [[lat, lng], ...],     // 지도에 그릴 경로
      // 실시간 생성 코스: 어떤 길로 가는지 (길이 비율). 인도 없는 차도(car_lane)는 항상 0
      "road_mix": { "sidewalk": 0.68, "car_free": 0.24, "alley": 0.08, "car_lane": 0, "crossing": 0, "unknown": 0 },
      "sidewalk_only": false,        // 골목도 지나지 않고 인도·차 없는 길·횡단시설로만 가는가
      "access_m": 62,                // 코스 시작점이 현위치에서 50m 이상 떨어져 있을 때, 거기까지의 거리
      "steps": [{ "description": "우회전 후 오동도로를 따라 213m 이동",
                  "turn_type": 13, "cum_m": 812.4 }]   // cum_m: 출발점부터 이 안내까지 거리(m)
    }
  }]
}
```

턴바이턴은 현재 위치의 누적 거리가 `cum_m`에 가까워질 때 해당 `description`을 안내하면 됩니다.

### `POST /feedback`

```json
{ "user_id": "u123", "course_id": "yeosu-coastal-01", "rating": 4,
  "aspects": { "elevation": "hard", "stops": "many", "scenery": "good" },
  "comment": "신호가 많았어요" }
```

`aspects`와 `comment`는 선택이다. 문항과 값은 `GET /onboarding/feedback`에서 받는다.

추천받은 코스를 뛴 뒤 1~5점을 보냅니다. 무엇 때문에 추천했는지는 서버가 추천 시점에 기억해 두므로 코스 id와 점수만 보내면 됩니다. 응답으로 갱신된 가중치와 설명(`explanation`)이 옵니다.

## 추천 방식

규칙 기반 가중치 점수(학습 데이터 불필요). 항목: 거리, 고도, 안전, 신호등 밀도, 풍경 태그, 시간대, 날씨.

- **목적·동반자**에 따라 가중치를 조정하고, 동반자는 거리·고도 상한도 적용 (예: 유아차는 고도 40m 이하)
- **시간대**: 야간엔 인적 드문 길 감점, 한낮엔 그늘(녹지) 우대
- **안전 점수**: CCTV 밀도 + 편의점 밀도(야간 유동인구) + 지구대·파출소 거리
- **거리**: 긴 코스는 목표 거리로 잘라서 반환. 왕복은 반환점을 당겨 출발점으로 돌아옴
- **코스 형태는 세 가지**: 왕복은 저장된 편도 코스에 실제 복귀 경로를 붙이고, 편도는 그대로 쓴다. **순환**은 저장된 편도 코스를 되짚는 대신, 목표 거리로 가상 꼭짓점을 잡아 OSM 보행로에 스냅하고 Tmap 경유지로 **실제 순환 코스**를 만든다(자기 교차 검사 + 각도·반경을 바꿔 재시도). 한 번 만든 루프는 DB에 쌓이고, 같은 자리·같은 거리 요청이면 다시 만들지 않고 그걸 쓴다
- 왕복의 복귀 구간도 실제 경로·안내 사용 (좌표를 뒤집지 않음)
- **실시간 생성도 요청한 풍경을 따라간다.** 주변 지형에서 그 풍경(강·해안·공원 등)에 닿는 길 위 지점을 경유지로 잡는다. 바다나 큰 강 건너편은 경유지로 잡지 않는다(다리를 찾아 멀리 돌게 되므로). 근처에 저장된 코스가 있어도 요청한 풍경에 맞는 게 없으면 그 자리에서 만든다

## 경로를 직접 짠다 (Tmap 최단거리 탈피)

Tmap 보행자 경로는 **최단 거리**를 준다. 러닝 코스로는 맞지 않는다 — 강변 산책로가 옆에 있어도 한 블록 안쪽의 빠른 길로 잇는다. 로컬 지형 데이터가 있으면 실시간 생성은 받아 둔 전국 도로망에서 **경로를 직접 탐색**한다 ([src/recommend/road_graph.py](src/recommend/road_graph.py)).

- **인도 없는 차도는 한 구간도 지나가지 않는다** ([src/recommend/sidewalk.py](src/recommend/sidewalk.py)). 길을 넷으로 나눈다:

  | 길 | 판단 근거 | 취급 |
  |---|---|---|
  | 차 없는 길 | OSM 보행·자전거 전용길 | 그대로 쓴다 |
  | 인도 있는 차도 | OSM `sidewalk` 태그 또는 Tmap 확인 | 그대로 쓴다 |
  | 골목·이면도로 | OSM 주택가 길·생활도로·통로 | 2~4배 길게 쳐서 **불가피할 때만** |
  | 인도를 모르거나 없는 차도(간선도로) | — | **지나가지 않는다** |

  OSM 한국 데이터에는 인도 유무가 거의 없어서(전국 약 9천 개 길), 경로에 인도를 모르는 간선도로가 있으면 **Tmap 보행 네트워크에 물어 확인한다**. Tmap은 구간마다 인도 분리(21) / 차 없는 보행로(23) / 인도 분리 없음(22)을 준다. 인도가 있으면 그 길을 쓰고, 없거나 확인되지 않으면 도로망에서 빼고 다시 짠다(최대 4번). 끝내 피할 수 없으면 그 코스는 **내보내지 않는다**
- 확인한 결과는 `data/sidewalk_facts.sqlite`에 쌓인다(길마다 인도 있음/없음). 한 번 확인한 길은 다시 묻지 않으므로 쓸수록 Tmap 호출이 줄어든다
- 경로는 직접 짠 것을 **그대로** 내보낸다. Tmap은 확인에만 쓴다 — Tmap 경로로 바꾸면 경유지 사이를 최단 거리로 이어 강변 같은 구간을 벗어난다(여의도에서 강변 41% → 11%로 떨어지는 것을 확인하고 바꿨다)
- 골목 비율은 `road_mix.alley`로, 출발 지점에서 코스 시작점까지 50m 이상 떨어져 있으면 그 거리를 `access_m`으로 준다
- **길마다 '달리기 좋은 정도'(0~1)를 매기고**, 점수가 낮은 길은 최대 3배 길게 쳐서 탐색한다. 조금 돌더라도 좋은 길로 간다
- **길 점수는 학습한다** ([src/recommend/learn_roads.py](src/recommend/learn_roads.py)). 정답은 사람들이 OSM에 달리기·걷기·자전거 코스로 등록해 둔 길(한강·탄천 자전거길 등). 같은 동네의 나머지 길과 비교해 길 종류·물가·공원·다리·터널 등 23개 특징의 가중치를 로지스틱 회귀로 배운다. 자전거 코스의 차도 구간과 등산로는 정답에서 뺀다. 결과는 `data/road_model.json`
- 순환은 **이미 지나간 길을 4배 길게** 쳐서 왔던 길로 돌아오지 않게 한다
- **밤에는 사람이 있는 길로 간다.** 낮에 좋은 강변·공원·숲 산책로가 밤에는 인적이 드물고 어둡다. 시간대가 밤이면(요청의 `time_of_day`, 없으면 서버 시각 21~05시) 길을 셋으로 나눠 탐색 비용을 바꾼다:

  | 밤의 길 | 판단 | 비용 |
  |---|---|---|
  | 사람이 있는 길 | 상점이 60m 안에 있거나, 인도가 있는 큰길이거나, 조명이 표시된 길 | 그대로 |
  | 보통 | 주택가 길 등 | 1.3배 |
  | 인적 드문 길 | 상점도 조명 표시도 없는 공원·숲·물가의 보행로 | 2.5배 |

  코스에 `lively_ratio`·`secluded_ratio`(길이 비율)와 `planned_for_night`가 붙고, 밤 시간대 점수(`time_fit`)는 이 값으로 계산한다. 가로등 데이터가 없어서(아래 한계) 상점과 큰길을 "밝고 사람이 있다"의 대리 지표로 쓴 것이다
- **실시간 생성 코스의 안전 점수를 실제로 계산한다.** 예전에는 0.7 고정값이었다. 저장된 코스와 같은 기준(CCTV 밀도 + 편의점 밀도 + 지구대·파출소 거리)으로 그 자리의 시설에서 계산하고, 신호등 수도 경로 25m 안의 실제 신호등을 센다
- 턴바이턴 안내도 도로망에서 만든다 (방향이 35° 이상 꺾이는 갈림길에서만). Tmap과 같은 `turn_type`을 쓴다
- Tmap은 경로를 **고르는** 데가 아니라 인도인지 **확인하는** 데만 쓴다(요청 하나에 0~3회, 아는 동네는 0회)
- 로컬 지형 데이터가 없으면 예전처럼 Tmap 최단 경로로 만들고, 골목과 차도를 구분하지 못한다

## 풍경 선택지 (사용자에게 보여주는 것)

측정 태그는 16종이고 기준이 "경로의 40% 이상이 해안선 200m 이내" 같은 식이라 고르는 사람에게 어렵다. 앱에는 **10가지 선택지**만 보여준다 ([src/recommend/scenery_choices.py](src/recommend/scenery_choices.py)).

| 묶음 | 선택지 | 보여주는 설명 | 대응하는 측정 태그 |
|---|---|---|---|
| 물가 | 바다 | 바다를 보면서 달려요 | 바다뷰, 해변 |
| | 강·하천 | 물길 옆 산책로를 따라 달려요 | 강변 |
| | 호수 | 호수나 저수지 옆을 달려요 | 호수 |
| 자연 | 공원 | 공원 안이나 공원 옆을 달려요 | 공원 |
| | 숲 | 나무가 우거진 길을 달려요 | 숲길, 산길 |
| 길 | 차 없는 길 | 차가 다니지 않는 산책로·자전거길로 달려요 | 차없는길, 보행자길, 자전거길 |
| | 캠퍼스·운동장 | 대학 캠퍼스나 운동장 옆을 달려요 | 캠퍼스, 운동장 |
| 볼거리 | 도심 | 가게가 많은 시내를 달려요 | 도심 |
| | 명소·전망 | 유적·명소나 전망 좋은 곳을 지나요 | 역사문화, 전망 |
| | 다리 건너기 | 큰 다리를 건너요 | 다리 |

`GET /onboarding/scenery` 응답 한 항목:

```json
{ "value": "강·하천", "label": "강·하천", "group": "물가", "hint": "물길 옆 산책로를 따라 달려요",
  "distance_km": 0.24, "near": "걸어서 3분", "course_count": 7 }
```

- `value`를 그대로 `/recommend`의 `environment_tags`에 넣는다. 선택지 하나는 대응 태그 중 **하나만** 지나도 만족한 것으로 본다
- `near`는 거리를 말로 바꾼 것이다(바로 근처 / 걸어서 N분 / N.Nkm). `group` 순서는 응답의 `groups`
- 추천 결과의 코스에는 `scenery_labels`(예: `["바다", "공원"]`)가 붙는다. 코스 카드에는 이걸 보여주면 된다
- 측정 태그 이름(`바다뷰` 등)을 보내도 예전처럼 동작한다

## 풍경 태그 (내부 측정 기준)

태그는 **경로가 실제로 그 지형을 얼마나 지나는지** 재서 붙인다 ([src/data_collection/scenery.py](src/data_collection/scenery.py)). 경로를 25m 간격으로 다시 찍고, 그 점들 중 몇 %가 해당 지형 안이나 바로 옆에 있는지를 본다.

| 태그 | 붙는 기준 | 코스 수 |
|---|---|---|
| 바다뷰 | 경로의 40% 이상이 해안선 200m 이내 | 5 |
| 강변 | 경로의 30% 이상이 강·하천 옆 | 7 |
| 호수 | 경로의 10% 이상이 호수·저수지 옆 | 2 |
| 공원 | 경로의 15% 이상이 공원 안이나 바로 옆 | 7 |
| 숲길 | 경로의 20% 이상이 숲 안 | 3 |
| 산길 | 숲길이면서 km당 25m 이상 오름 | 0 |
| 보행자길 | 경로의 30% 이상이 보행자 전용길 | 2 |
| 자전거길 | 경로의 15% 이상이 자전거도로 | 2 |
| 차없는길 | 경로의 절반 이상이 차가 다니지 않는 길 | 1 |
| 다리 | 200m 이상 이어지는 다리를 건넘 | 4 |
| 역사문화 | km당 유적·박물관·명소 2곳 이상 | 6 |
| 전망 | 경로 150m 이내에 전망 포인트 | 9 |
| 도심 | 상점이나 신호등이 촘촘한 시내 구간 | 16 |
| 해변 · 캠퍼스 · 운동장 | 각각 경로의 15% / 15% / 10% 이상 | 0 |

- 기준은 26개 실제 코스의 측정값을 코스 이름과 대조해 정했다. **코스가 하나도 없는 태그는 선택지로 나가지 않는다**(`/onboarding/scenery`) — 골라도 결과가 0개인 선택지를 만들지 않기 위해서다. 해당 코스가 추가되면 자동으로 나타난다
- 같은 태그라도 **정도가 점수에 반영된다**: 경로의 100%가 해안인 코스가 41%인 코스보다 앞선다
- 선은 꼭짓점이 아니라 선분까지의 거리로 잰다(해안선은 꼭짓점이 수백 m씩 떨어져 있다). 면은 안에 있으면 경계에서 멀어도 지나는 것으로 본다. 다리는 총 길이가 아니라 **끊기지 않고 이어진 최장 구간**으로 잰다 — 천변길이 다리 밑을 여러 번 지나는 것을 "다리를 건넌다"로 잡지 않기 위해서다
- 실시간으로 만든 코스에도 **요청값이 아니라 측정값**으로 태그를 붙인다. 강변을 요청해 강 쪽으로 만들었어도 실제로 30%를 못 채우면 강변 태그는 붙지 않고, 그런 코스만 나오면 `404`와 이유를 준다
- 저장된 26개 코스의 태그는 `courses.json`에 이미 들어 있어 바로 동작한다. 실시간 생성에 쓰는 지형은 아래 **로컬 지형 데이터**에서 읽고, 없으면 Overpass로 동네당 한 번 받아 `data/osm_cache/`에 둔다
- **벚꽃길·야경·일출 같은 태그는 만들지 않았다.** OSM에 판정할 데이터가 없어서 붙이면 추측이 된다(가로등은 광주 전역에 0개)
- 도심 판정은 상점 밀도와 신호등 밀도 중 하나만 넘어도 인정한다. 지역마다 OSM 데이터가 한쪽씩 비어 있기 때문이다(광주는 상점, 여수는 신호등)

## 개인화 학습 (AI)

사용자마다 중요하게 여기는 게 다르다(신호등을 못 참는 사람, 오르막이 있어도 경치가 좋으면 만족하는 사람). 설문으로 다 물을 수 없으니 **러닝 후 만족도로 사용자별 가중치를 학습**한다 ([src/recommend/personalize.py](src/recommend/personalize.py)).

- **콜드 스타트**: 첫 추천 요청의 온보딩 값(숙련도·목적·동반자·선호 풍경)을 초기 설문으로 저장하고 기본 가중치에서 시작
- **학습**: 평가받은 코스가 **같이 추천됐던 다른 코스들보다** 어느 항목에서 강했는지를 본다. 만족했는데 신호등 항목이 두드러졌다면 신호등 가중치를 올리고, 불만족이면 내린다
  - 갱신식(지수 경사): `w_k ← w_k · exp(η · r · (s_k − s̄_k))`, `r = (평점−3)/2`, `s̄_k` = 다른 추천 코스들의 평균
  - 절대 점수가 아니라 다른 선택지와의 **차이**로 학습한다. 그래야 모든 코스가 목표 거리에 맞았을 때 거리 가중치가 괜히 오르지 않는다
  - 학습률은 평가가 쌓일수록 줄어든다(처음엔 빠르게 적응, 나중엔 한 번의 평가에 덜 흔들림). 각 가중치는 0.03~0.45로 제한해 한 항목이 무시되거나 독점하지 않게 한다
- **효과**: 기본 가중치로 2위였던 코스가 **평가 3번 만에 1위**로 올라온다(테스트로 확인)
- **항목별 답으로 직접 배운다.** 별점 하나로는 무엇이 좋았는지 알 수 없어 위 방식은 다른 코스와의 차이로 *추정*한다. 그래서 러닝 후 5가지를 따로 묻는다(각 3지선다, 건너뛸 수 있음):

  | 질문 | 답 | 배우는 것 |
  |---|---|---|
  | 거리는 어땠나요? | 짧았어요 / 딱 좋았어요 / 길었어요 | 거리 가중치 ↑ + 시간으로 고를 때의 환산 거리 ±7% |
  | 오르막은 어땠나요? | 너무 평탄했어요 / 적당했어요 / 힘들었어요 | 고도 가중치 ↑ + 이 사람의 오르막 목표 ±15% |
  | 자주 멈췄나요? | 거의 안 멈췄어요 / 보통 / 자주 멈췄어요 | 신호등 가중치 |
  | 풍경은 어땠나요? | 좋았어요 / 보통 / 별로였어요 | 풍경 가중치 |
  | 안심됐나요? | 안심됐어요 / 보통 / 불안했어요 | 안전 가중치 |

  - 답은 그 항목에 대한 직접 증거라 **그 항목의 가중치만** 고친다. 불만(+1)은 "이 사람에게 중요하다"는 강한 증거, 칭찬(+0.5)은 약한 증거, "보통"(−0.25)은 별로 신경 쓰지 않는다는 증거로 본다
  - "힘들었어요/길었어요"처럼 **방향이 있는 답은 목표값을 옮긴다.** 같은 "보통 오르막"도 사람마다 다르기 때문이다. 오르막은 0.5~1.8배, 거리는 0.7~1.4배 안에서만 움직이고, 거리를 km로 직접 고른 요청은 건드리지 않는다
  - 테스트: 오르막 "보통"을 고른 사람이 언덕 코스에 "힘들었어요"를 3번 답하면 다음 추천 1위가 평탄한 코스로 바뀐다
  - `GET /profile/{user_id}`의 `summary`는 사용자에게 그대로 보여줄 수 있는 문장이다(예: "신호등에 자주 멈추는 걸 불편해하세요 (2번 말씀하셨어요)"). **실제로 답한 내용에 근거가 있는 것만** 말한다
- **설명**: `GET /profile/{user_id}`는 기본값보다 몇 % 더/덜 중시하게 됐는지를 준다. 합을 1로 맞추면서 무관한 항목이 같이 오르는 몫은 빼고 계산한다 — 안 그러면 "날씨를 중시한다" 같은 틀린 설명이 나온다
- 학습된 취향·평가 이력·후기·즐겨찾기(`data/app.sqlite`)는 개인 데이터라 `.gitignore` 대상이다

### 사용자 DB — 각자 자기 취향을 볼 수 있게

`data/app.sqlite` (SQLite, 서버가 처음 쓸 때 자동 생성, 저장소에는 올리지 않음).

| 테이블 | 내용 | 단위 |
|---|---|---|
| `profiles` | 학습된 가중치, 오르막·거리 기준, 초기 설문, 항목별 답 누적 | 사용자당 1행 |

### 로그인 — 본인만 자기 데이터를 본다

```
POST /auth/signup  {"username": "runner", "password": "········", "guest_id": "demo-ab12cd34"}
→ {"user_id": "acct-9f2c1e…", "username": "runner", "token": "…"}
```

이후 요청에는 `user_id`로 받은 값을 쓰고, 헤더에 `Authorization: Bearer <token>`을 붙인다.

| 상황 | 응답 |
|---|---|
| 계정의 `user_id`인데 토큰이 없거나 만료 | `401` |
| 다른 사람의 토큰 | `403` |
| 로그인하지 않은 손님 id (`demo-…`) | 예전처럼 그대로 동작 |

- 보호되는 요청: `/recommend`(`user_id`를 줄 때), `/feedback`, `/reviews`, `/favorites`, `/profile/{id}`, `/users/{id}/taste`, `DELETE /users/{id}`
- **가입 전 데이터가 이어진다.** 가입할 때 `guest_id`(로그인 없이 쓰던 기기의 id)를 주면 그동안 쌓인 취향·평가 이력·즐겨찾기가 계정으로 옮겨진다
- **비밀번호는 저장하지 않는다.** 계정마다 다른 소금을 넣어 scrypt로 해시한 값만 둔다. 토큰도 SHA-256 해시만 저장하고 30일 뒤 만료된다
- 아이디가 없을 때와 비밀번호가 틀렸을 때 같은 답(`401`)을 준다. 같은 아이디로 5분 안에 5번 틀리면 `429`
- 후기 목록에는 내부 `user_id` 대신 `author`(아이디 또는 "러너")만 나간다
- `DELETE /users/{id}`는 계정까지 지운다(회원 탈퇴)
- **실제 서비스는 HTTPS로만 써야 한다.** 평문 HTTP에서는 비밀번호와 토큰이 그대로 지나간다. 비밀번호 찾기·이메일 인증·소셜 로그인은 없다

## 로컬 지형 데이터 (선택, 권장)

실시간 생성은 출발점 주변의 길과 지형이 필요하다. 기본은 Overpass API인데 건당 5~20초에 실패(504·429)가 잦다. 같은 데이터를 파일로 한 번 받아 두면 **실행 중 Overpass 호출이 0건**이 된다.

```bash
python -m src.setup_local                   # 위 "빠른 시작"의 설치 스크립트가 이것까지 해 준다
python -m src.data_collection.local_osm     # 지도 DB만 따로 만들 때 (팀 기준 날짜 파일, 결과 약 880MB)
```

받는 지도 파일은 날짜를 고정했다(`south-korea-260929.osm.pbf`, MD5 확인). "latest"를 받으면 받은 날마다 데이터가 달라서 같은 요청에도 사람마다 다른 경로가 나온다. 지도를 새 날짜로 바꿀 때는 `local_osm.py`의 `PBF_URL`·`PBF_MD5`·`BUILD_VERSION`을 같이 바꾸고 팀 전원이 설치 스크립트를 다시 돌린다.

| | Overpass (기본) | 로컬 지형 데이터 |
|---|---|---|
| 새 동네 첫 순환 요청 | 13~20초, 실패 시 풍경 유도 없이 생성 | 3~12초 |
| 경로 | Tmap 최단 거리 | 직접 탐색 (좋은 길 우선) + 인도 확인 |
| 인도 없는 차도 | 구분 못 함 | 지나가지 않음 |
| 현위치 주변 풍경 선택지 | 근처 저장 코스 기준 | 실제 지형 기준, 거리 포함 |
| 지원 지역 | 받아 본 동네 | 전국 |
| 설치 | 없음 | 위 명령 1회 |

- 안 만들어도 서버는 그대로 동작한다(자동으로 Overpass 사용). 파일은 저장소에 올리지 않는다
- 지도 DB가 어떤 파일·어떤 버전으로 만들어졌는지 DB 안에 기록되고, `/health`의 `local_map`에서 확인할 수 있다
- 길이 막다른 길인지는 변환할 때 전국 도로망으로 판정해 둔다. 경유지는 막다른 길에 잡지 않는다
- 길 점수 모델(`data/road_model.json`)은 저장소에 들어 있어 다시 학습할 필요 없다. 다시 하려면 `python -m src.recommend.learn_roads --cells 2496`
- 내려받기가 안 되면 https://download.geofabrik.de/asia/south-korea.html 에서 `.osm.pbf`를 직접 받아 `--pbf 경로`로 준다

- **개인화 학습을 추가했습니다.** 러닝 후 만족도로 사용자별 가중치를 학습합니다(`user_id`, `POST /feedback`, `GET /profile/{user_id}`). 데모 화면에선 도착 후 별점을 매기면 반영됩니다.
- 지도 타일이 늦게 뜨면 내비게이션(안내·남은 거리·도착·음성)이 통째로 멈추던 문제를 고쳤습니다.
- **풍경 태그를 측정 기반으로 다시 만들었습니다.** 4종 → 13종. 예전 `숲길`은 26개 중 22개에 붙어 있어 골라도 걸러지는 게 없었습니다(지금은 숲 안 구간이 20% 이상인 3개). 선택지는 `GET /onboarding/scenery`에서 받으세요
- **순환 코스의 군더더기를 없앴습니다.** 경유지가 막다른 길에 찍혀 들어갔다 되나오던 구간(실측 4.84km 중 0.74km)을 잘라내고, 해안가에선 바다 쪽 대신 길이 있는 방향에만 경유지를 잡습니다. 목표 거리의 40%도 안 되는 후보와 사실상 같은 길인 후보는 걸러냅니다. 5km 요청 시 1위 결과: 여수 5.07km · 광주 4.99km · 해운대 4.66km, 되짚는 구간 1.3% 이하
- **Tmap 최단거리 대신 경로를 직접 짜고, 인도로만 가게 합니다** (로컬 지형 데이터 필요). 학습된 길 점수로 경로를 고른 뒤 Tmap 보행 네트워크로 인도인지 확인하고, 인도 없는 차도가 있으면 피해서 다시 짭니다. 실측 9건(광주·여수·대전·해운대·여의도·망원동) 전부 차도 0%, 골목 0~8%. 예: 광주 강변 순환 5km → 4.43km·강변 67%, 여수 바다뷰 순환 4km → 4.12km·바다뷰 44%, 여의도 강변 순환 6km → 6.37km(Tmap 경로로는 만들지 못하던 곳)
- **목적지 경로에도 같은 규칙을 적용했습니다.** 8km 이내 목적지는 도로망에서 직접 짜서 인도 없는 차도를 피하고 밤에는 사람 있는 길로 갑니다. 그렇게 갈 길이 없으면 Tmap 경로를 주되 `no_car_lanes: null`(확인 못 함)로 표시합니다
- 데모 화면에 즐겨찾기(코스 카드의 ☆, 목록에서 다시 불러오기)를 넣었습니다
- 실측(낮 → 밤, 인적 드문 길 비율): 광주 상무 순환 37% → 0%, 해운대 28% → 2%, 망원동 31% → 7%, 여의도 31% → 22%. 밤에는 인적 드문 구간이 가장 적은 후보만 남기므로 거리가 덜 맞을 수 있습니다(여의도 6km 요청에 4.09km)
- **팀원 환경을 기준 PC와 똑같이 맞추는 설치 스크립트를 넣었습니다** (`python -m src.setup_local`). 지도 파일 날짜를 고정하고, 인도 확인 기록을 씨앗 파일로 공유합니다. `/health`에 `local_map`(지도 DB 출처·일치 여부)과 `sidewalk_facts`(아는 길 수)가 추가됐습니다

- **목적지 검색을 Tmap 장소 검색으로 바꿨습니다.** 예전 검색(Nominatim)은 "스타벅스"를 오키나와로, "오동도"를 섬 한복판 좌표로 줬습니다. 지금은 현위치 주변을 우선하고, 걸어서 들어가는 입구 좌표를 쓰고, 후보 목록(`GET /places`)에서 고를 수 있습니다

- **현위치 주변에 실제로 있는 풍경만 선택지로 줍니다** (`/onboarding/scenery?lat=&lng=`). 내륙에서는 '바다'가 나오지 않습니다
- **별점·후기·즐겨찾기를 저장합니다** (`/feedback`의 `comment`, `/reviews`, `/favorites`). 추천 결과에 다른 사용자의 평균 별점이 같이 나갑니다
- **실시간 생성이 요청한 풍경을 따라갑니다.** 예전에는 아무 방향으로 만든 뒤 풍경을 재서 아니면 버렸습니다(광주 강변 요청 → 강변 14~22%로 결과 없음). 지금은 풍경 위에 경유지를 잡습니다: 광주 강변 5km → 4.4km·강변 49%, 여수 바다뷰 4km → 4.24km·바다뷰 46%
- **Overpass 없이 돌릴 수 있습니다** (`python -m src.data_collection.local_osm`, 위 "로컬 지형 데이터"). 전국 어디서든 첫 요청 4~8초, 외부 지형 호출 0건
- **실시간 편도·왕복의 거리를 고쳤습니다.** 5km 편도 요청에 1km가 나오고, 왕복은 복귀 구간 없이 나가던 문제입니다. 왕복은 절반을 나갔다가 실제 복귀 경로로 돌아옵니다
- 근처 저장 코스에 요청한 풍경이 없을 때 빈 결과(200)를 주던 문제를 고쳤습니다. 그 자리에서 만듭니다
- 만들어 둔 루프는 재사용합니다. 출발점이 600m 이내이고 목표 거리와 20% 이내로 맞으면 다시 만들지 않습니다(재요청 1초 이내, Tmap 호출 0건).
- 이미 닫힌 루프에 왕복 처리를 또 하던 문제를 고쳤습니다(6.8km 코스가 13.6km로 나가던 문제).
- 테스트 격리를 추가했습니다. 이전에는 테스트가 실제 코스 DB에 코스를 등재하고 Tmap 할당량을 소모했습니다.

## 알려진 한계

- 가로등 데이터 없음(OSM에 한국 데이터 부재). CCTV는 공식 데이터가 아닌 OSM 기준이라 실제보다 적게 잡힘
- 풍경을 따라가는 순환은 지형에 따라 거리가 목표와 10~30% 어긋날 수 있다
- 인도 확인은 Tmap 구간을 15m 안의 OSM 길에 맞춰 적는 방식이라, 길 양쪽 중 한쪽에만 인도가 있는 경우까지는 구분하지 못한다. 큰길을 **건너는** 지점에 횡단보도가 있는지도 확인하지 않는다
- 직접 짠 경로의 턴바이턴 안내에는 횡단보도·육교 안내가 없다(방향 전환만 안내)
- 저장된 26개 코스는 인도 확인을 거치지 않았다(Tmap 보행 경로이긴 하다). 실시간 생성 코스에만 적용된다
- **가로등 데이터가 없다.** OSM에 조명이 표시된 길은 전국 약 8천 개뿐이라, 밤 경로는 상점·큰길을 대신 본다. 실제 밝기는 모른다. 지자체 가로등·보안등 공공데이터를 받으면 같은 구조에 넣을 수 있다
- CCTV도 OSM 수집분이라 실제보다 적게 잡힌다
- 길 점수의 정답(공개 코스)은 자전거길에 치우쳐 있다. 달리기 코스로 등록된 길은 전국에 100개 남짓이라, 앱에 쌓이는 별점으로 다시 학습하는 것이 다음 단계다
- Tmap 무료 등급 하루 1,000건 — 실시간 왕복 생성 1회에 2건 사용
- 데모 지도(MapLibre + OpenFreeMap)는 OSM 기반이라 상호 정보가 Tmap보다 적음. 경로·안내 데이터는 Tmap
